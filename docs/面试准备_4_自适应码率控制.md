# 自适应码率控制 —— 面试准备文档

## 一、架构总览

```
┌──────────────┐        ┌─────────────┐ ┌───────────────────────────┐
│ RTMP SDK     │──stats─▶│ NetMonitor  │──signal─▶│ DynamicBitrateController │
│ (Metrics)    │        │ (质量评估)   │        │ (决策引擎)        │
└──────────────┘  └─────────────┘        └────────────┬──────────────┘
     │ setBitrate()
              ▼
    ┌──────────────┐
          │  VEncoder    │
        │  (NVENC调参) │
       └──────────────┘
```

### 数据流
```
RTMP Publisher 定时 Metrics::snapshot()
    → NetMonitor::updateRtmpStats(snapshot)
        → 计算 jitter + networkLevel
        → emit statsUpdated(snapshot)
  → DynamicBitrateController::onStatsUpdated() [缓存最新stats]
    → monitorTimer(1s) → onMonitorTimerTimeout() [决策]
        → VEncoder::setBitrate(newBitrate)
```

## 二、11 维信号详解

| # | 信号名 | 来源 | 计算方式 |
|---|--------|------|----------|
| 1 | `bytesSent` | RTMP SDK | 累计 socket send() 字节数 |
| 2 | `bytesAcked` | RTMP SDK | 服务器 Acknowledgement 确认的字节数 |
| 3 | `bytesInflight` | 计算 | `bytesSent - bytesAcked`（网络积压量） |
| 4 | `sendThroughputBps` | RTMP SDK | EWMA(α=0.3) 实际发送吞吐量 |
| 5 | `encodeInputBps` | 编码器 | EWMA(α=0.3) 编码器产出码率 |
| 6 | `rttMs` | RTMP SDK | RTMP Ping/Pong 往返延迟 |
| 7 | `jitterMs` | NetMonitor | RTT 历史（10次）的标准差 |
| 8 | `videoQueueDelayMs` | RTMP SDK | 视频发送队列排队延迟 |
| 9 | `audioQueueDelayMs` | RTMP SDK | 音频发送队列排队延迟 |
| 10 | `socketWriteBlockMs` | RTMP SDK | 单次 socket 可写等待的 P95 值 |
| 11 | `droppedVideoFrames` | RTMP SDK | 累计丢弃的视频帧数 |

### Jitter 计算
```cpp
// 维护最近 10 个 RTT 样本
rttHistory_.append(rttMs);
if (rttHistory_.size() > 10) rttHistory_.pop_front();

// 总体标准差 σ
average = Σ(rtt) / N;
variance = Σ((rtt - average)²) / N;
jitter = sqrt(variance);
```

### EWMA 吞吐量
```cpp
// 每 500ms 采样一次
int64_t deltaBytes = currentBytesSent - lastSampleBytes;
int instantBps = deltaBytes * 8 * 1000 / 500;  // 转为 bps
sendThroughputBps = 0.3 * instantBps + 0.7 * sendThroughputBps;  // α=0.3
```

## 三、网络质量分级（NetMonitor）

| Level | 含义 | 触发条件（OR） |
|-------|------|----------------|
| 3 (Bad) | 严重 | `vqDelay≥1000ms` \| `writeBlock≥500ms` \| `rtt≥500ms` |
| 2 (NotBad) | 中等 | `vqDelay≥400ms` \| `writeBlock≥150ms` \| `rtt≥200ms` \| `jitter≥80ms` |
| 1 (Normal) | 轻微 | `vqDelay≥150ms` \| `writeBlock≥50ms` \| `rtt≥120ms` \| `jitter≥40ms` |
| 0 (Good) | 健康 | 以上均不满足 |

## 四、拥塞判断（11 个子条件，任一为 true 即判定拥塞）

| # | 子条件 | 表达式 | 含义 |
|---|--------|--------|------|
| 1 | dropped | `droppedFrames > previousDropped` | 有新丢帧 |
| 2 | queueHigh | `vqDelay≥350ms \| aqDelay≥500ms` | 队列严重堆积 |
| 3 | queueRising | `vqDelay≥180ms && (当前-上次)≥60ms` | 队列持续增长 |
| 4 | writeBlocked | `socketWriteBlock≥150ms` | 写阻塞 |
| 5 | throughputDeficit | `vqDelay≥150ms && send < encode×92%` | 发送能力不足 |
| 6 | backlogGrowing | `vqDelay≥150ms && inflightIncrease>256KB` | 网络积压增长 |
| 7 | latencyCorroborates | `vqDelay≥150ms && rtt≥350ms` | 高RTT佐证 |
| 8 | localQueuePressure | `vPktQueue>20 \| aPktQueue>35` | 本地包堆积 |
| 9 | sendStalled | `encode>500kbps && send<100kbps` | 发送完全停滞 |
| 10 | massiveInflight | `bytesInflight>10MB` | 巨量未确认 |
| 11 | highRttWithDrops | `rtt≥300ms && dropped` | 高RTT+丢帧 |

---

## 五、恢复判断（所有条件同时满足）

| # | 子条件 | 表达式 |
|---|--------|--------|
| 1 | noNewDrops | `droppedFrames == previousDropped` |
| 2 | queuesHealthy | `vqDelay<100ms && aqDelay<150ms && vqDelay≤prev+20ms && vPkt≤5 && aPkt≤8` |
| 3 | transportHealthy | `writeBlock<50ms && (rtt≤0 \| rtt<250ms)` |
| 4 | inflightCleared | `bytesInflight<2MB` |
| 5 | sendResumed | `sendThroughput > encodeInput × 80%` |

## 六、状态机与决策逻辑

### 采样 & 确认机制
```
每 1s 触发 onMonitorTimerTimeout():
  → 判断 isCongested / isRecovered
  → 拥塞: congestedSamples++, recoveredSamples=0
  → 恢复: recoveredSamples++, congestedSamples=0
  → 两者都不是: 两个计数器清零
```

### 降码率触发条件
- `congestedSamples >= 2`（连续2次判定拥塞）
- 距上次调整 ≥ 2.5s（冷却时间）

### 升码率触发条件
- `recoveredSamples >= 8`（连续8次判定恢复）
- `currentBitrate < initBitrate`（当前低于初始值）
- 距上次调整 ≥ 10s（冷却时间）

## 七、降码率分级策略

| 级别 | 触发条件 | 系数 | 效果 |
|------|----------|------|------|
| 重度 | `vqDelay≥1000ms \| writeBlock≥500ms \| dropped \| inflight>20MB` | ×0.68 | 降32% |
| 中度 | `vqDelay≥500ms \| writeBlock≥250ms \| inflight>10MB` | ×0.75 | 降25% |
| 轻度 | 其他拥塞 | ×0.82 | 降18% |

### 附加约束
```cpp
// 不超过可持续带宽的 90%
if (sendThroughput > initAudioBitrate + minVideoBitrate) {
    sustainableVideo = (sendThroughput - initAudioBitrate) * 0.90;
    target = min(target, sustainableVideo);
}

// 最终钳位
minBitrate = max(initVideoBitrate * 0.4, 300000);  // 下限
target = clamp(target, minBitrate, initVideoBitrate);
```

## 八、升码率策略

```cpp
// 加性增长步进
int64_t step = max(50000, initVideoBitrate / 20);  // 至少50kbps

// 目标码率
int64_t target = min(initVideoBitrate, currentVideoBitrate + step);
```

**示例**：初始码率 2.5Mbps → 步进 = max(50k, 125k) = 125kbps/次

## 九、NVENC 参数动态调整

### 初始化配置
```cpp
codecCtx_->bit_rate = config.bitrate;
codecCtx_->gop_size = framerate * 2;     // 2秒关键帧间隔
codecCtx_->max_b_frames = 0;     // 禁用B帧（低延迟）
codecCtx_->pix_fmt = AV_PIX_FMT_NV12;

// NVENC 私有参数
av_opt_set(priv_data, "preset", "p3", 0);       // 低延迟预设
av_opt_set(priv_data, "rc", "cbr", 0);       // 恒定码率
av_opt_set_int(priv_data, "surfaces", 16, 0);   // 异步表面数
```

### 运行时 setBitrate
```cpp
void VEncoder::setBitrate(int targetBitrate) {
    lock_guard<mutex> lock(codecMutex_);

 // FFmpeg 通用参数
    codecCtx_->bit_rate = targetBitrate;
    codecCtx_->rc_max_rate = targetBitrate;       // CBR: max=target
codecCtx_->rc_min_rate = targetBitrate;       // CBR: min=target
    codecCtx_->rc_buffer_size = targetBitrate * 2; // VBV 缓冲 = 2s
    codecCtx_->bit_rate_tolerance = targetBitrate / 4;

    // NVENC 私有选项
    av_opt_set_int(priv_data, "bitrate", targetBitrate, 0);
    av_opt_set_int(priv_data, "max_bitrate", targetBitrate, 0);
    av_opt_set_int(priv_data, "min_bitrate", targetBitrate, 0);
}
```

**注意**：`codecMutex_` 保证 `setBitrate` 与 `encode` 不并发。

## 十、与 RTMP SDK 背压的联动

```
        ┌─────────────────────────┐
            │  DynamicBitrateController│
       │  (主动降/升码率)          │
          └──────────┬──────────────┘
      │
              ┌────────────────┼────────────────┐
      ▼    ▼       ▼
    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
    │ VEncoder     │  │ PacketQueue  │  │ RTMP SDK     │
    │ (码率调整)│  │ (本地缓冲)   │  │ (三级背压)    │
    └──────────────┘  └──────────────┘  └──────────────┘
```

**分工**：
- **RTMP SDK 背压**：应急机制（队列已严重堆积时丢帧保实时）
- **ABR 控制器**：预防机制（根据趋势提前调整码率避免堆积）
- **两者互补**：ABR 降低了产出速率 → SDK 背压触发频率降低

## 十一、开发中遇到的问题与解决方案

### 问题 1：码率频繁震荡（升→降→升→降）

**现象**：码率每隔 10-15s 就在高低之间来回跳动，画质不稳定。

**原因**：升码率后立即消耗了所有网络余量，1-2s 后又触发拥塞降码。恢复判断（8次）和冷却时间不够保守。

**解决**：
1. 升码率冷却时间从 5s → 10s
2. 恢复所需连续样本从 5 → 8
3. 升码率后将 `recoveredSamples` 清零，重新积累
4. 升码率步进从 10% → 5%（或固定 50kbps），加法增更温和

---

### 问题 2：弱网恢复后码率回升极慢

**现象**：网络恢复正常后，码率仍停在低位长达数分钟。

**原因**：恢复判断条件 `sendThroughput > encodeInput × 80%` 在低码率时几乎总是满足（因为编码产出也低了），但 `vqDelay < 100ms` 条件在低码率下确实容易满足，问题在于 `congestedSamples` 清零逻辑有 bug——当判定"既不拥塞也不恢复"时两个计数器都清零，导致恢复计数器始终无法累积到 8。

**解决**：修改逻辑——只有判定拥塞时才清零恢复计数器，"中间态"不清零：
```cpp
if (isCongested) {
    congestedSamples_++;
    recoveredSamples_ = 0;  // 拥塞时清零恢复
} else if (isRecovered) {
    recoveredSamples_++;
    congestedSamples_ = 0;  // 恢复时清零拥塞
}
// 中间态：两个计数器都保持不变
```

---

### 问题 3：Stats 数据过期导致误判

**现象**：RTMP SDK 断线重连期间，ABR 控制器基于最后一次 stats 持续判定拥塞并把码率降到最低。

**原因**：断线期间 Metrics 停止更新，但 ABR 控制器仍然每秒采样旧数据，旧数据中 `vqDelay` 值已过时。

**解决**：引入 `StatsStaleTimeoutMs = 3000`，如果距离上次 stats 更新超过 3s，则跳过本轮决策：
```cpp
if (now - lastStatsTime_ > StatsStaleTimeoutMs) {
    return;  // 数据过期，不做决策
}
```

---

### 问题 4：NVENC setBitrate 后码率没有实际变化

**现象**：调用 `setBitrate()` 后日志显示参数已更新，但实际输出码率不变。

**原因**：FFmpeg 的 `avcodec_open2()` 后，部分编码器的 `AVCodecContext` 字段变为只读。直接修改 `bit_rate` 等字段不会生效，必须通过 `av_opt_set` 设置编码器私有选项。

**解决**：同时设置 FFmpeg 通用字段（为了一致性）和 NVENC 私有选项（真正生效的）：
```cpp
// 通用字段（部分编码器会读）
codecCtx_->bit_rate = targetBitrate;
// 私有选项（NVENC 真正读取的）
av_opt_set_int(codecCtx_->priv_data, "bitrate", targetBitrate, 0);
av_opt_set_int(codecCtx_->priv_data, "max_bitrate", targetBitrate, 0);
```

---

### 问题 5：高 jitter 导致过度降码

**现象**：WiFi 环境下 RTT 波动大（30~150ms），jitter 经常超过 80ms 触发 Level 2，但实际吞吐量充足。

**原因**：jitter 单独作为拥塞信号权重过高。WiFi 天然 RTT 抖动大，但带宽可能完全够用。仅凭 jitter 判断拥塞会误判。

**解决**：jitter 不直接作为拥塞判断的独立条件，只参与 `networkLevel` 评估（辅助信息）。拥塞判断的 11 个子条件中不包含单独的 jitter 阈值——它通过 `latencyCorroborates`（RTT≥350ms + 队列堆积）间接参与，避免单一信号误判。

---

### 问题 6：升码率后第一帧 I 帧超大导致瞬间拥塞

**现象**：升码率后 NVENC 产生一个非常大的 I 帧（码率翻倍），瞬间触发拥塞→又降回去。

**原因**：CBR 模式下升码率后，VBV buffer 有余量，编码器倾向于把攒的 "budget" 一次性用在下一个关键帧上。

**解决**：
1. `rc_buffer_size` 设为 `targetBitrate * 2`（2秒缓冲），限制瞬时峰值
2. 升码率后不立即清空 VBV buffer（保持渐进填充）
3. 降码率时触发的计数器清零操作增加 1s 延迟，给第一个大帧消化时间

## 十二、面试必须掌握的知识点

### 1. AIMD 策略（Additive Increase Multiplicative Decrease）
- TCP 拥塞控制的经典策略
- **乘性减**：检测拥塞时码率 × 系数（0.68~0.82），快速释放带宽
- **加性增**：恢复后码率 + 固定步长（50kbps），保守试探上限
- **为什么不用 MIMD（乘性增乘性减）？** 上升太快容易再次拥塞
- **为什么不用 AIAD（加性增加性减）？** 下降太慢无法及时响应

### 2. 为什么需要多维信号？
- 单一信号容易误判（如 RTT 高但吞吐量正常 = 路由器缓冲大）
- 多维交叉验证提高判断准确性
- 不同信号有不同的响应速度：
  - 丢帧（最快，已经发生了损害）
  - 队列深度（中速，趋势预判）
  - inflight（慢速，全局积压）

### 3. 为什么用 OR 判断拥塞，AND 判断恢复？
- **拥塞判断宁可过敏不可漏报**：任何一个信号异常都应该警惕
- **恢复判断宁可保守不可冒进**：所有信号正常才能确认恢复
- 这保证了系统的**稳定性优先**

### 4. 冷却时间的意义
- 防止短时间内多次调整导致震荡
- 给网络和编码器时间"消化"上一次调整
- 降码率冷却 2.5s < 升码率冷却 10s → 降快升慢，保守为主

### 5. CBR vs VBR 在直播场景的选择
| | CBR | VBR |
|-|-----|-----|
| 输出码率 | 恒定 | 变化 |
| 网络压力 | 可预测 | 峰值可能突破带宽 |
| 画质 | 简单场景浪费，复杂场景不足 | 按需分配 |
| 适合场景 | **直播**（带宽有限，需要稳定） | 录制（存储不敏感） |

### 6. VBV (Video Buffering Verifier)
- 模拟解码器缓冲区
- `rc_buffer_size` = 缓冲区大小
- 防止编码器在某帧"透支"太多码率导致后续帧质量断崖式下降
- CBR + VBV = 真正的恒定码率

### 7. 为什么禁用 B 帧？
- B 帧需要双向参考，增加编码延迟（至少多一帧）
- 直播场景延迟敏感，每多一帧缓冲 = 多 16-33ms 延迟
- B 帧使 DTS ≠ PTS，增加 muxing 复杂度

### 8. EWMA 的意义
- Exponentially Weighted Moving Average（指数加权移动平均）
- α=0.3：新值权重 30%，历史权重 70%
- 平滑突发波动，反映趋势而非瞬时值
- α 越大越敏感，α 越小越平滑
